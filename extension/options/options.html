Providers

Choose the model the hub agent uses. Pick a provider, paste your key, test it, and click Use. Your API key stays on this device only — never in the bundle or receipts. Logs are redacted unless you explicitly enable full local detail under Advanced.

Provider server tools Let agents activate tools the provider executes inside the model call (no local code runs). Today: Google Search grounding (Gemini) and web search (Anthropic). Cost: 5,000 free searches/mo shared (Gemini 3.x), then $14 per 1,000 searches — CAP shows estimates only; the provider's free-tier meter is not visible here.

Agents that may use provider-run tools

Each enabled agent can run provider-side web searches during its tasks. Usage is billed by the provider; estimates appear below.

MCP servers

Connect a remote MCP server so agents can call its tools. Only remote servers are supported — Streamable HTTP or SSE over an https:// URL. An auth token stays on this device only — never in the bundle, logs, or receipts — and is never shown again after you save it.

Local folders & files

Manage persistent access to local directories and files granted to agents or tasks. Access is restricted to the specific folder or file subtree and can be revoked at any time.

File System Access API is unavailable in this browser environment

Tool library

Read-only diagnostics: the tools the platform can see, grouped by what they are for. Nothing here runs, installs, grants, updates, or removes tools.

Add a Site Agent

Chrome grants <all_urls> host access when the extension is installed; page tools require it. The capabilities in Permissions are separate optional permissions, requested only when you enable or use them.

Site tool permissions

A Site Agent can report tools after enrollment, but the first model use of each exact tool asks you. Allowed tools run automatically until you disable them here; denied tools stay blocked until you allow or reset them.

Board permissions

Every named agent and the hub can post and claim jobs on the shared board. A rule blocks one specific edge.

Browser control

Open, navigate, and close tabs, and capture screenshots need your explicit, scoped permission. Reading page text and listing tabs are always available.

Allow the agent to control the browser Open, navigate, and close tabs, and capture screenshots.
Auto-close run tabs When a task finishes, close the tabs that task opened (the run summary lists them), except tabs the agent opened as the task's result to leave for you. Off by default; windows a task opened are never closed automatically, and tabs it already closed itself are never touched.

Allowed origins

Every site you allow keeps its own grant; turn one off without touching the others.

Adding origins scopes control to the listed sites. To allow every site again, turn the switch off and back on.

Action policy

What the agent may do once Browser control is on, in three classes.

  • Read Read page text, list tabs. Allowed after consent — never interrupts.
  • Act Open, navigate and manage tabs, groups, bookmarks and page actions. Asks once per site, then runs automatically.
  • Destructive Close a tab it didn't open, close a window, wipe browsing data, remove a bookmark, or set/remove a cookie. Always asks — each action shows an approval card.

Permissions

Capability permissions are optional and requested just-in-time from your click (the chat offers the same Enable inline). Host access and the permissions the extension needs to run are granted at install. This is the live, verified state of each grant.

Skills

Reusable capabilities, each documented below. A skill is included in a task — type /skill:name anywhere in the composer on the hub, or attach it to an agent. Use one here to start a task with it pre-filled.

System hooks

Every chrome.* event an agent can listen to and respond to. Turn a hook off to stop the agent ever using it — the deny-list is authoritative and the agent cannot break past it. A hook's permission is granted at install; the deny-list is the control here.

System prompts

The system prompt each agent runs with, layer by layer: the versioned built-in prompt, your customization, and the protected runtime policy (never editable, always applied last). The preview is the exact platform composition; every run also records a run-bound attestation of the exact provider-bound system message (digest + bytes, never content).

Data & memory

Per-origin memory is stored in OPFS, keyed by origin — one site can never read another. Browse each agent's memory below.

Run logs

Every run keeps its record and its answer. Its step-by-step tool detail is kept in full for the newest runs and folded into a one-line summary for older ones, so storage stays bounded.

Keep every run log Off: full detail for the newest 50 runs per task and the newest 500 runs overall (up to 32 MiB); older runs keep a summary line.

Agent data maintenance

Purge agent journals (the running activity logs — memory content and artifacts are kept), or clean up leftover files from agents that were removed before deletion cleaned up after itself.

Backup & restore

Export everything you have built — agents, memories, threads, artifacts, schedules and settings — as one inspectable file. Provider API keys and MCP auth headers are never included; the file only records which providers were configured.

Factory reset

Permanently delete all extension data — agents, tasks, artifacts, memory, schedules, downloaded models, provider settings, and permissions. Restores the clean first-run onboarding state.

## 1. The verified baseline

The product works. This is measured, at the baseline commit, in one clean run:

| Gate | Result | Notes |
|---|---|---|
| `node build.mjs` | pass | 2.8 MB SW bundle; AST scan over 72 shipped files clean; gallery synced |
| `deno test -A tests/` | **633 pass, 0 fail** | Green only with `TMPDIR` pointed at durable storage. On the host's default temp filesystem the suite fails at `tests/cdp-client.test.ts` with `No space left on device`. Same commit, same code, two results — a direct demonstration of `CAP-FB-20260821-WORKTREE-HYGIENE-01`. |
| `scripts/chrome-journeys.ts` | **126/126 pass** | Real loaded MV3 extension: enrollment, disenroll races, management tools, owner approvals across a service-worker restart, no SW console errors, clean profile teardown |
| Hub render | 62 ms `domContentLoaded`, 65 ms `load` | Budget is 1 s |
| Fresh-profile boot | zero permissions, zero CSP violations | One honest warning: storage ungranted, session-only |

Reading the source confirms the architecture is real, not claimed:

- `agent-do` is imported from npm and wrapped in `lib/agent.js`, not reimplemented.
- Sender authorization derives origin from the content script's own realm; page senders
  hit a route allowlist; `sender.tab.url` is never trusted.
- Tool descriptors are validated as zod schemas; no `z.record(z.any())` bypass.
- All 65 `innerHTML` assignment sites outside `dist/` route untrusted values through
  `escapeHtml`/`escapeAttr`.
- The manifest ships `"permissions": []` with no `debugger` anywhere.

**Conclusion: code quality is not this project's problem.** Do not spend the next
increment hardening what is already hard.

## 2. The problem

Commits landing on `origin/main`, per day:

| Date | Commits | Code-touching |
|---:|---:|---:|
| 14 Aug | 4 | 4 |
| 15 Aug | 55 | 52 |
| 16 Aug | 70 | 61 |
| 17 Aug | 83 | 76 |
| 18 Aug | 65 | 62 |
| 19 Aug | 20 | 14 |
| 20 Aug | 3 | 2 |
| 21 Aug | 0 | 0 |

A 96% collapse in 72 hours. It begins on **19 August**, the day the crash-recoverable
tracker landed and the day after the mandatory handoff lifecycle took effect.

Four mechanisms produce it. Each has a task.

### 2.1 The terminal state is unreachable

The lifecycle is nine states ending in `CONFIRMED`, which requires explicit
product-owner confirmation per task. Across 31 tracked tasks, **zero are `CONFIRMED`**.
Four sit at `PUSHED` with `Next: obtain confirmation`, some since 18 August.

Because nothing retires, the tracker only grows, and new tasks inherit a dependency
graph of unretired ancestors — six of the fifteen currently-open tasks name another
open task as a blocker. → `CAP-FB-20260821-PUSHED-TASK-CLOSEOUT-01`,
`CAP-FB-20260821-DELIVERY-LIFECYCLE-01`

### 2.2 Rebasing has become the work

The tracker's own words, on three separate entries:

> *"READY_FOR_BROWSER only on old base; not deliverable… the accepted delta must be
> recreated and independently checked on `ffbdf28` before browser use."*

Work passes review → main advances → the review is voided by the base change → the work
is recreated → it needs review again. With serialized integration and one browser queue,
a lane can never catch up. This is the mechanism that converted finished code into
**46 branches ahead of `origin/main` that will never land**.
→ `CAP-FB-20260821-STALE-BRANCH-TRIAGE-01`

### 2.3 Evidence production has displaced delivery

The private coordination ledger holds 322 open handoff records. None are closed:

| Handoff state | Count |
|---|---:|
| `BLOCKED` | 152 |
| `FIX_REQUESTED` | 82 |
| `INTEGRATING` | 62 |
| `REVIEW_PASSED` | 15 |
| `PUSHED` | 5 |
| `REVIEWING` / `RECEIPT_ACKED` | 6 |

72% are `BLOCKED` or `FIX_REQUESTED`. Lanes are producing versioned acceptance
*packages* — v7, v8, v9, v10, v11, v14, v15, v16 of the same work — that are statically
reviewed and rejected before a browser ever runs. No lane that reached v8 or beyond has
produced a browser result. → `CAP-FB-20260821-DELIVERY-LIFECYCLE-01`

### 2.4 The tracker has lost contact with the repository

This is the finding to act on first, because it makes `TASKS.md` actively misleading.

Fifteen tasks read `Owner: unassigned`, `Branch: none`, `Candidate: —`. At least nine
have committed implementation work in branches right now:

| Task (tracker says unassigned / no branch) | Work that exists |
|---|---|
| `CAP-FB-20260819-CONVERSATION-RUN-STATUS-01` (P0) | `feat/overnight-conversation-status-nub` |
| `CAP-FB-20260819-COMPOSER-AGENT-MENTIONS-01` (P1) | `feat/composer-agent-mentions` (+3) and a detached candidate |
| `CAP-FB-20260819-DURABLE-BACKGROUND-RUNS-01` (P0) | four branches, up to +6 |
| `CAP-FB-20260819-PERMISSION-REMEDIATION-UX-01` (P0) | `docs/permission-remediation-design` (+5) |
| `CAP-FB-20260819-AGENT-DELETION-LIFECYCLE-01` (P1) | `docs/agent-deletion-lifecycle` (+3) |
| `CAP-FB-20260819-SITE-AGENT-STATUS-CLEANUP-01` | `fix/site-agent-copy-status-cleanup` (+2) |
| `CAP-FB-20260819-LOCAL-MODEL-MANAGEMENT-01` | `feat/gemma4-catalog-preflight` |
| `CAP-FB-20260819-PAGE-SCOPED-SITE-IDENTITY-01` (P1) | a detached candidate on the temp filesystem |
| `CAP-FB-20260819-DIRECTORY-TOOL-EXPLORER-01` (P1) | three directory branches |

The join key is broken at the root. The tracker exists so a stable `CAP-FB-*` ID links a
task to its commits. **2 of 430 commits mention a `CAP-FB-*` ID.** Every `Recover:` field
in `TASKS.md` prescribes a `git grep` that cannot find its own work.
→ `CAP-FB-20260821-TRACKER-GIT-RECONCILE-01`

### 2.5 Some lanes are producing nothing

Seventeen worktrees sit at exactly `origin/main` with zero commits. Ten share the naming
pattern `cap-page-identity-directory-prep-v3` … `-v13` — identical checkouts of the same
tip with no work in any of them. The same shape appears in the scheduled-task lane
(v14, v15, v16) and the durable lane (v9, v10, v11): create a versioned prep directory,
fail a static review, increment the version, repeat.

Any agent that finds itself creating a `-vN+1` directory without a commit in `-vN` should
stop and escalate rather than increment.

## 3. Verified defects

Each is reproduced at the baseline commit. All are also recorded in
[`KNOWN-ISSUES.md`](KNOWN-ISSUES.md).

### D1 — Temp-filesystem inode exhaustion is degrading the machine · **P0**

The build/test host's temporary filesystem reports **1,043,303 of 1,048,576 inodes used
(100%)**. This is what failed the unit suite, and it will fail any process on that host
needing a temp file — not only this project.

Roughly 60 full git worktrees live there at ~7,560 inodes each, alongside 235
`cap-picker-full-*` and 104 `cap-run-status-evidence-*` retained evidence bundles.

The cleanest demonstration: the same unit suite on the same commit is **633/0** with
`TMPDIR` on durable storage and fails outright on the default temp filesystem. Any gate
result produced on this host is currently a measurement of its disk, not of the code.

**That filesystem is tmpfs — RAM-backed.** A reboot destroys all of those worktrees and
every retained evidence bundle referenced by a `Gates:` field in `TASKS.md`. Evidence
whose only copy is on tmpfs is not durable evidence.
→ `CAP-FB-20260821-WORKTREE-HYGIENE-01`

### D2 — Seven commits were reachable only from RAM-backed worktree HEADs · **P0, mitigated**

Seven detached worktrees on the temp filesystem held commits unreachable from any branch.
The objects live in the main repository, but the only refs pointing at them were the
worktree HEADs; on reboot they become unreachable and eligible for `git gc`.

One is `b4a0a6f feat(composer): route agent mentions canonically across named, background
and site agents` — an implementation of a task the tracker calls unstarted.

**Mitigated:** all seven are now tagged `rescue/tmp-detached-<short-sha>` in the local
repository. The tags are local and unpushed; nothing was deleted. Run
`git tag -l 'rescue/*'` to list them. Do not delete a temp worktree until its HEAD is
reachable from a branch or one of these tags.
→ `CAP-FB-20260821-WORKTREE-HYGIENE-01`

### D3 — Runs are not durable; they execute inside a message handler · **P0**

The `run-task` route calls `runTask()` directly inside `chrome.runtime.onMessage`. There
is no persisted in-flight run record — `activeRuns` in `lib/scheduler.js` is an in-memory
`Map`. The service worker's own comment states the dependency:

> *"The port keeps the SW alive while a page is listening."*

A long agent run's survival therefore depends on a UI page holding the `agent-progress`
port open. Close the hub tab and the run is gone: tool side effects already committed, no
result, no resume. Tool calls are journalled for replay, but the run cannot be
reconstructed from them.

This is exactly `CAP-FB-20260819-DURABLE-BACKGROUND-RUNS-01` (P0). The finding is recorded
here as independent confirmation that the task is correctly scoped and correctly rated —
and that it has four branches of work against it while the tracker lists it unassigned.

### D4 — WebMCP discovery status renders outside its card · **P2**

`ntp/ntp.html` sets `.panel-body { padding: 4px 0; }` — no horizontal padding, so each row
supplies its own. `#webmcp-hub-status` carries the `panel-body` class but has **no CSS
rule anywhere in the repository**, and `ntp/ntp.js:113` writes straight into
`el.textContent`. The result — *"Discovery has not run yet."* — sits flush against the
panel edge, roughly 14 px left of every sibling row, visibly breaking the card boundary.

Reproduced in a screenshot of a clean build of the baseline. Present in no tracker.
→ `CAP-FB-20260821-WEBMCP-STATUS-ALIGNMENT-01`

### D5 — A fresh install looks broken and offers no way forward · **P1**

New profile, zero permissions: the hub shows empty states and a red error-console badge
reading **1**. The entry is honest — *"storage permission not granted — changes are
session-only until enabled in Settings"* — but a first-time user reads a red badge as a
fault.

The deeper issue is what "session-only" means under MV3. Without the optional `storage`
permission, `lib/kv.js` degrades to an in-memory `Map` owned by the service worker, and
MV3 terminates idle workers after roughly 30 seconds. A user who enters an API key
without granting storage loses it almost immediately, with no warning at the point of
entry.

There is no onboarding flow anywhere in the extension — grepping for `first-run`,
`onboard`, and `welcome` finds only unrelated hits.
→ `CAP-FB-20260821-FIRST-RUN-ONBOARDING-01`

### D6 — The standalone run-status banner is still live on main · **P0, already tracked**

`ntp/ntp.js:1192` still binds `document.getElementById("run-status")` and sets a generic
top-of-thread state. `CAP-FB-20260819-CONVERSATION-RUN-STATUS-01` is P0 precisely because
`ffbdf28` fixed lifecycle *ownership fencing* and was mistaken for fixing the
*presentation*. Any agent taking that task must confirm it understands the distinction
before starting; this is the kind of item that gets re-closed without being fixed.

### D7 — Three files carry too much of the system · **P2**

`background/service-worker.js` is 4,799 lines exposing **127 message routes** in one flat
handler object. `shared/components.js` is 5,193 lines with 33 custom elements.
`options/options.js` is 1,775 lines.

This is why every change needs cross-subsystem review and why lanes conflict so readily —
the serialized integration queue is partly compensating for this shape. It is also why
`AGENTS.md` needs a rule reminding agents to grep for couplings: the couplings are not
expressible in the module structure.
→ `CAP-FB-20260821-SW-ROUTE-MODULARIZATION-01`

### D8 — The recipes → skills rename never finished · **P3**

The UI says "Skills". The code ships `extension/recipes/`, `lib/recipes.js` at 655 lines,
and `options/options.js` importing `RECIPES` — while `lib/skills.js` is 39 lines.
`ntp/ntp.js:1586` reads `openView("recipes/index.html", "Skills")`. `AGENTS.md` cites this
rename as *the* example of cross-subsystem drift; it is still drifting.
→ `CAP-FB-20260821-RECIPES-SKILLS-RENAME-01`

## 5. Where the plan is under-exploited

Not defects — direction. Each is deliberately *not* opened as a task, because they need a
product decision from the owner first.

**Lead with sites-as-sub-agents.** This is the genuinely novel claim and the one nothing
else does. It is currently buried behind an unstyled Directory page and a discovery status
line that renders outside its card. A curated set of real origins exposing useful WebMCP
tools, reachable in two clicks from the hub, would demonstrate the whole thesis in thirty
seconds. Everything else in the product is table stakes by comparison.

**Make the permission model the feature, not the tax.** `"permissions": []` is a real
differentiator against every other agent extension and is currently experienced as
friction. `docs/permission-remediation-design.md` already specifies the right thing.
Shipping it turns the hardest constraint into the first thing people notice.

**Semantic tool search is the right next architectural bet — but not yet.**
`CAP-FB-20260820-SEMANTIC-TOOL-SEARCH-01` is well-aimed: with 127 message routes, a
management toolset, and an unbounded per-site WebMCP catalog, context pressure will bind
long before model quality does. It is meaningless while runs die when a tab closes.
Sequence it after `CAP-FB-20260819-DURABLE-BACKGROUND-RUNS-01`.

## 7. Proposed rule changes

These change how the fleet works and need the owner's decision before an agent applies
them. They are captured under `CAP-FB-20260821-DELIVERY-LIFECYCLE-01`.

1. **Cut the lifecycle from nine states to four:** `OPEN → IN_REVIEW → MERGED → DONE`.
   Keep the two rules that are load-bearing — a *different* model reviews, and a *real
   browser* drives it. Delete content-addressed gate evidence, remote attestation, and the
   separate `GATED`/`READY_FOR_BROWSER`/`INTEGRATING`/`PUSHED`/`CONFIRMED` distinctions.
   Nine states have produced 322 open handoffs and zero confirmations.
2. **`CAP-FB-…` in the commit subject becomes mandatory.** Today it is 2 commits out of
   430, which means the tracker's own recovery procedure does not work.
3. **A review is valid for its content, not its base.** If a candidate passed review and
   main advanced without touching the same files, the review stands. Re-review only what
   actually changed. This alone ends the rebase treadmill.
4. **No worktree on tmpfs.** Worktrees and retained evidence live on durable storage.
5. **No `-vN+1` without a commit in `-vN`.** An agent that would create the next versioned
   attempt with no committed work in the previous one stops and escalates instead.
6. **Optimise for one visible increment per day**, not for an unfalsifiable audit trail.
   The 126/126 journey suite is a strong gate. It is sufficient.

# Full-Suite Chrome and Test Gate Contract

**Status:** Authoritative Contract (chrome-agent-platform-dqc1 / CAP-FB-20260908-FULL-SUITE-CHROME-CONTRACT-01)  
**Applies to:** `npm test`, `npm run test:changed`, `npm run test:file`, `scripts/run-tests.mjs`, `scripts/select-tests.mjs`, `scripts/test-partition.mjs`, `scripts/chrome-journeys.ts`, and all KAT harnesses.

---

## 1. Executive Summary

This document specifies the exact execution environment, real-browser requirements, and lock contracts for the Chrome Agent Platform test gates.

A reader or scheduler must not infer the absence of Chrome from names like "pure", "unit", or "unitScope":
1. **`npm test` includes a real-browser test when Chrome is available.** In `tests/chrome-profile-location.test.ts` (the `9t1b: a REAL browser holds its profile while the whole tree is copied` test near line 97), `browserRefusal(...)` guards the launch. If no usable browser resolves, the last test in that file emits a named, counted environmental refusal (exit **75** via `scripts/lib/browser-refusal.ts`), never a pass or a product failure.
2. **Launch scopes distinguish lock contention, not browser execution.** A `lockPath` (caller-owned file) ensures a test does not block or queue behind machine-wide acceptance runs; it is **NOT** a flag for "no browser". If `binary: fake` is omitted, `launchChrome()` launches real Chromium.
3. **Subset gates (`npm run test:changed`) cannot see cross-cutting guards.** A guard test that is neither modified nor in the static reverse-dependency path of changed files does not run. `npm test` is the mandatory pre-push gate precisely because cross-cutting guards (partition guard, substring honesty, machine-path honesty, etc.) only run when the full suite executes.

## 2. Real-Browser Requirements by Gate and Phase

### 2.1 The Full Test Gate (`npm test` / `scripts/run-tests.mjs`)
The full gate runs in two sequential phases:

**Exit-code vocabulary (chrome-agent-platform-5xg1w).** The runner's exit code is a verdict, not just a
success flag: **0** completed green · **1** completed, product red (every selected file ran) ·
**75** environmental refusal · **76 INCOMPLETE** — the run selected files it did NOT execute (a test
seam declined a phase, or a phase was killed by its bound while the rc was not a kill code): NOT a
verdict on the tree, and a gate cache must not file it as a FAIL (the manifest carries
`outcome:"incomplete"` and `skipped:N`, and the run's LAST log line is the cache-visible marker
`ABORTED: incomplete suite run — … phase not entered, skipped=N`) ·
**124/137/143** a bound killed the run (also never a verdict; these outrank 76 so the kill stays
named). A serial-phase failure NO LONGER skips the parallel phase (chrome-agent-platform-0o0um): the
full parallel phase still runs, so the completed run exits **1** — a genuine product red whose log
carries every parallel result, adjudicable and cacheable. Manifest `skipped` is NARROW by contract: it
counts selected files with no certified result from a DECLINED or LOST lane/phase (planner skips, seam
declines, serial-lane children that exited without reporting, and parallel children that never
spawned); files lost inside a phase killed
mid-flight are named in `incomplete` with that phase's own progress instead, so `skipped: 0` beside
`outcome: "incomplete"` never means complete coverage. A completed FAIL is byte-identically
distinguishable from an abort: exit 1 with
`outcome:"failed"` vs exit 76 with `outcome:"incomplete"`.

- **Phase 1: Serial Phase (20 hazard files)**
  - Runs build-artifact hazard tests serially with per-file process isolation and bounded timeouts (`scripts/lib/serial-phase.mjs`): 180s per file at idle, scaled by load per CPU OR measured hypervisor CPU steal (the larger of the two) up to 720s — sampled per file at the wait, never once per run, after steal-blindness killed a 64.7%-steal gate at the flat bound with zero scaling lines (chrome-agent-platform-8qy5d). An explicit `CAP_SERIAL_TEST_TIMEOUT_MS` overrides this without scaling. EVERY measured window prints its decision line — scaled (`run-tests: serial timeout scaled to …`) or not (`run-tests: serial window … not scaled: …`) — each carrying the measured load and steal at the wait, so a dead run's log always names what the box was doing.
  - For callers using a ready marker, `serial-runner.mjs` starts the execution timeout **after** the marker appears. At the ready deadline it measures load per CPU: an idle or unmeasurable host refuses the absent marker with exit 124 and a named reason; a measured loaded host gets one announced grace window bounded at ×4 the original ready budget, then still refuses with exit 124 if no marker appears. A child exiting without a marker refuses immediately. `READY_MARKER_LOADED_GRACE` and `READY_MARKER_TIMEOUT_*` in stderr distinguish delayed boot from an actual missing marker; a loaded classification is not a passing verdict.
  - **Browser requirement:** NONE of the serial files launch a real browser. Lock-machinery tests (`tests/chrome-launch-lock.test.ts`, `tests/chrome-launch-lock-scope.test.ts`, `tests/chrome-slot-semaphore.test.ts`, `tests/chrome-slot-semaphore-honesty.test.ts`) test concurrency and locking logic using `binary: fake` (a mock process printing DevTools banners).
- **Phase 2: Parallel Phase (422+ files)**
  - Runs all non-hazard test files concurrently via `deno test --parallel`. The full and changed-test runners print the candidate file names to stdout and stderr before this phase; on timeout they print the immediate timeout notice and a named candidate block to both streams. Parallel scheduling cannot identify which candidate hung, so the block labels the culprit unconfirmed rather than blaming every file.
  - **Browser requirement:** The profile-copy test and the embedded Settings canary require a usable real browser to execute, but absence is an **environmental refusal**, not an executed product failure.
    - `tests/chrome-profile-location.test.ts` (test title near line 97) first checks `browserRefusal(resolveChromiumBinaryReport(), BROWSER_DEPENDENT_TESTS)` near line 119. Only if it returns `null` does the test reach the real `launchChrome({ extension: `${ROOT}/extension`, profile, timeoutMs: 25000, lockPath: lockScope })` call near line 141.
    - `tests/kat-embedded-settings-canary.test.ts` exercises the embedded-Settings iframe contention canary (`scripts/kat-gi0jw-activity-approval.ts --settings-only`), bounding child execution via `runBoundedChild` and asserting the 6 Settings PASS checks under parallel-phase contention. If no browser resolves, it issues a typed environmental refusal via `browserRefusal(...)` / `refuseWithoutBrowser(...)` (exit 75).
    - This test exercises the live race condition where Chrome holds and continuously churns its profile (`Default/`, `SingletonLock`, WAL) outside the repository while a copy of the working tree executes concurrently. The copy is `rsync -a` of the repository **minus four bulk directories** (`/node_modules/`, `/.git/`, `/packages/bundled/evidence/`, `dist-versions/`), not literally every byte (jjsz: copying them dominated the suite). That does not weaken the property: the race needs a profile inside the copied tree, the launcher never puts one in any of those four directories (the profile root is outside the repository, asserted by an earlier test in the file), and the profile-signature scan reads the REAL tree, excluded directories included. `rsync` is therefore a host prerequisite (§6). The test name still says "whole tree" because it is a stable identifier cited elsewhere.
    - If no executable browser resolves, the browser-dependent tests decline; after the remaining static tests, the last test calls `refuseWithoutBrowser(...)` (near line 492), prints the named/count diagnostics, and exits **75** via `scripts/lib/browser-refusal.ts`. Exit 75 is neither a pass (0) nor a product red (1). If a browser resolves but its actual launch fails for another reason, diagnose that failure rather than calling it this missing-browser refusal.
    - Other parallel test files in `tests/` are in-memory unit tests, mock Web/DOM tests, or static source scanners that require no browser.

### 2.1d The parallel-phase file order and its off switch (`CAP_PARALLEL_SCHEDULE`)
The parallel phase's WORKER COUNT is Deno's default, but its FILE ORDER is the repo's own:
`scripts/lib/parallel-schedule.mjs` sorts the selected files longest-first, using the weights in
`scripts/lib/test-weights.json`, so the heaviest files start first and their tails overlap the light
ones instead of the whole phase finishing on the last heavy file. This does not change WHICH files
run: the runner selects files first (`scripts/select-tests.mjs`, `defaultTestPlan`) and the schedule
is a permutation of that selection, pinned by `tests/parallel-schedule.test.ts`, which also rejects a
weight naming a file that is no longer in the parallel tier (renamed, removed, serial, build-deferred,
heavy-deferred or read-only-dist).
- **Off switch:** `CAP_PARALLEL_SCHEDULE=0` (`scripts/run-tests.mjs`) turns the ordering off and runs
the selected files in their selection order. It exists for diagnosis - a same-tree A/B of a
scheduling complaint - never as a fix for a red test; an unordered phase runs the same file multiset.
- **Where the numbers come from, and their limit:** the 54 weights are historical isolated-file wall
seconds measured on a **2-vCPU** VM at tree `1f79854` on **2026-10-08**, not timings for the current
tree. The 2026-10-15 refresh checked tier membership and removed five newly heavy-deferred names; it
recalibrated nothing. NO committed command re-measures the table, so a performance claim needs a
same-tree A/B rather than an inference from these numbers. The full derivation, the method, and what
a re-anchor owes (`npm run test:file -- tests/parallel-schedule.test.ts`) are in
`docs/TEST-COUPLING-INVENTORY.md` entry 23 and in the table's own `_provenance` block.

The input set is the **transitive closure of what the tier IMPORTS and what it EXECUTES BY PATH**, computed from the roots `build.mjs`, `scripts/build-gate.ts` and every `BUILD_GATE_FILES` entry: relative specifiers are resolved with this repo's `.mjs`/`.ts`/`.js`/`.json` and `/index.*` conventions, and each visited file's CODE (comments stripped, per o4m2) is scanned for repo path tokens such as `scripts/build-bundled-tool-packages.mjs`, `scripts/stubs/{gateway-stub,vercel-oidc-stub}.mjs` and `scripts/mcp-probe-entry.js`, which is how the build reaches child processes and esbuild entry points (chrome-agent-platform-21iey). Every relative specifier the walk cannot resolve is NAMED in the gate log instead of being assumed to be "no dependency", and a closure that ever exceeds 500 files reports `truncated` and RUNS the tier (a partial key must not certify). The rule and the safety argument live in `scripts/lib/build-tier-inputs.mjs`; `tests/build-tier-inputs.test.ts` pins it, including every dependency both findings named.

## 3. The Three Launch Scopes (`acquireLaunchScope`)

All browser launches go through `launchChrome()` in `scripts/lib/chrome-launch.ts`. The launcher enforces exactly one launch scope via `acquireLaunchScope()`. It starts the browser as its own session and process-group leader through `setsidSpawnSpec()` (`scripts/lib/process-tree.ts`): `/usr/bin/setsid` where it exists (Linux), otherwise `/usr/bin/perl -MPOSIX` calling `POSIX::setsid()` before `exec` (macOS ships no `setsid` binary). It records the dedicated process group from `/proc/<pid>/stat`, or from `/bin/ps -o pgid=` where there is no `/proc` (macOS); `teardownChrome(launched)` kills and verifies that entire group as well as matching the unique profile. `attachProcessLifeline()` adds a crash-safe watchdog (jjsz): it runs in its own session and blocks reading a pipe whose write end only the launching process holds, so if that process dies for any reason — including `SIGKILL` or a test runner killing its process group — the kernel closes the pipe and the watchdog kills the browser's group and every process whose argv carries the profile (a literal, end-anchored match: `lifelineMatchPattern` escapes every regex metacharacter, so a profile ending `/p1` never reaches `/p10`). A killed or timed-out test therefore cannot orphan Chrome. The lifeline is a small state machine (`armed` → `fired` | `disarmed`, once; `lifelineState()` reports it). When the browser's leader exits while the launcher is alive and no teardown is running (the shape of most acceptance scripts: `proc.kill("SIGKILL"); await proc.status`), that exit triggers a one-shot sweep through the watchdog's own kill logic, so a wedged helper is reaped without waiting for the launcher to die (measured on real Chrome for Testing with the helpers `SIGSTOP`ped: 7 survivors before, 0 after, about 60 ms). A normal `teardownChrome` disarms the watchdog only AFTER it has verified the group empty; a teardown that throws leaves it armed, and a teardown that starts while a sweep is running waits for the sweep, because the sweep's `pkill -f` also matches the teardown's own `pkill`/`pgrep` command lines (a normal teardown costs about 40 ms more than before, from the bounded `ps` wrapper). A watchdog that cannot be started (no perl, `EAGAIN`) says so once on stderr and the launch continues unprotected; whether to refuse the launch is a policy call for the caller. `attachProcessLifeline` refuses an unsafe `group` (anything but the leader's own pid, greater than 1) before it spawns anything. Where there is no `/proc` (macOS) the `/bin/ps` fallbacks fail closed: only `ps -p <absent pid>` exiting 1 with empty stdout and stderr proves a process gone, and every other outcome throws, so an unreadable process table is never read as an empty group. Encoding `--user-data-dir` in a descendant's `argv[0]` does **not** defeat `pkill -f`: it matches the joined cmdline (17/17 baseline descendants and 11/11 live group members matched). Group killing is defense in depth for a descendant that leaves the profile match or is born after it. The cause of the original confirmation miss remains open; the full gate plus the user-data-dir monitor is the deciding evidence. `chromeProfileDir()` supplies a fresh pid/time/random-suffixed profile per launch.

```
                          ┌─────────────────────────────┐
                          │   acquireLaunchScope(opts)  │
                          └──────────────┬──────────────┘
                                         │
                 ┌───────────────────────┼──────────────────────┐
                 ▼                       ▼                      ▼
        opts.lockPath           opts.canonicalLock           default
     (Caller-owned file)      (Machine-wide lock)      (4-slot semaphore)
             │                           │                      │
             ▼                           ▼                      ▼
    Flock caller tempfile       Flock /tmp/cap-*.lock     Flock /tmp/slot-*.lock
    Isolation: per-test        Isolation: machine-wide    Isolation: bounded (4)
    Used by: unit tests        Used by: journeys/sec      Used by: KAT harnesses
```

1. **Unit-Scope Lock (`opts.lockPath`)**:
   - Takes an exclusive lock on a caller-owned file (`Deno.makeTempFile`).
   - Purpose: Prevents unit test fixtures from queueing behind machine-wide acceptance runs and avoids depleting the machine's 4-slot concurrency semaphore.
   - **Critical Contract:** `lockPath` isolates lock files; it does **NOT** disable browser launching. If `opts.binary` is omitted, real Chromium is launched.
2. **Canonical Machine Lock (`opts.canonicalLock: true`)**:
   - Takes the exclusive lock at `/tmp/cap-serialized-chrome-acceptance.lock`.
   - Purpose: Machine-wide determinism across all concurrent CAP lanes on the machine. Reserved for suites whose evidence depends on strict single-instance execution (`scripts/chrome-journeys.ts` and security custody chain with `CAP_SECURITY_NONCE`).
3. **Bounded-Concurrency Semaphore (Default)**:
   - Takes one slot (0 to `CAP_CHROME_MAX_CONCURRENT - 1`, default 4) via `/tmp/cap-chrome-slot-N.lock`.
   - Purpose: Standard acceptance suites and KAT harnesses. Limits concurrent headless browsers across the system to prevent memory exhaustion and thrashing.

### 4.1 What the connect/reap-order pin checks, and what it does not

`tests/kafr4-suite-connect-inside-reaping-try.test.ts` is the structural pin behind kafr4 (a suite that
connects CDP *before* the `try` whose `finally` reaps the browser it launched never reaps it, and a hung
suite then holds a real Chrome for as long as it hangs). It is a parsed check — esbuild strips the types,
acorn parses what is left — so it is not fooled by anything spelled inside a comment, a string, a template
or a regex. It proves two things and only two:

- **REACH** — every `openCdp(...)` call under `scripts/` and `tests/` is written inside the try **block** of
  a try whose `finally` contains a reap call;
- **STRUCTURAL ORDER** — that reap is written as a direct statement of the `finally`, with no function,
  arrow or class between the call and the finalizer body, so it cannot be deferred into a helper the
  `finally` never calls.

It does **not** prove **execution** (a reap inside a branch that never runs still reads as guarded) and does
not prove **identity** (a `finally` that reaps a different platform object than the suite launched still
reads as guarded). Both are asserted in the test file as KNOWN LIMITATIONS rather than left to be discovered.
Proving execution is not a shape property; proving identity is dataflow. Dataflow is deferred until a suite
in this repo launches twice (chrome-agent-platform-d36q4 owns that decision and records the five review
rounds that got here).

The reason the boundary is written down rather than engineered away: the first four rounds of this pin each
fixed one lexical corner (block comments, template interpolations, regex literals) and each fix invited the
next, because the class was "a hand-written JavaScript lexer in a test". A pin that claims more than it
checks is worse than a pin that states its reach, because "checked" is what a reader takes away.

## 5. The Motivating Lesson: Subset Gates vs Cross-Cutting Guards

### 5.1 The Fundamental Limitation of Subset Gates
`npm run test:changed` builds an in-memory static reverse dependency graph (`importer -> imported`). It evaluates:
1. Which files were modified vs `origin/main`?
2. Which tests import those modified files directly or transitively?
3. Always include `CORE` (security + vocabulary).

**A cross-cutting guard does not import every file it inspects.** Guard tests (such as `tests/test-partition-guard.test.ts`, `tests/substring-pin-honesty.test.ts`, `tests/machine-path-honesty.test.ts`, `tests/harness-registry.test.ts`, `tests/durable-root.test.ts`, `tests/chrome-lock-fixture-scope.test.ts`) read file trees dynamically at runtime. Unless the guard file itself or one of its statically imported modules is modified, `npm run test:changed` will **never** select the guard.

### 5.2 Tonight's Case Study: How `main` Went Red
1. Commit `27ec8926` (`atve`) widened the durable-root guard and updated `tests/durable-root.test.ts`, adding a reference to `scripts/build-bundled-tool-packages.mjs`.
2. The partition classifier in `scripts/test-partition.mjs` scans all test files for `build.mjs` or `build-bundled-tool-packages`. Finding that reference, it classified `tests/durable-root.test.ts` as a build-artifact hazard.
3. Because `tests/durable-root.test.ts` had neither a `SERIAL_REASONS` entry nor an `EXEMPTIONS` entry, `tests/test-partition-guard.test.ts` failed (4 passed, 1 failed).
4. However, `atve` and subsequent authors iterated and validated using `npm run test:changed`. Because neither `test-partition.mjs` nor `test-partition-guard.test.ts` was in the diff or in `CORE`, `test-partition-guard.test.ts` was never executed.
5. As a result, four successive commits (`ffc4b263`, `ccdf3e23`, `c8a68d11`, `f75e6afb`) landed on `origin/main`, and `main` remained quietly broken for hours until a full `npm test` was run during `6yrq` verification.

### 5.3 Non-Negotiable Gate Rule
- `npm run test:changed` is exclusively for inner-loop rapid iteration.
- **`npm test` is the non-negotiable pre-push gate.** Never push or report done based solely on a passing subset run.

## 6. Build Speed, Concurrency Rules and Host Prerequisites (chrome-agent-platform-jjsz)

### 6.1 The parallel build and the rules that keep it safe

`build.mjs` runs the 12 esbuild bundles, the Zod-Doc scrub, the minify pass, the final whole-AST evaluator gate, Pyodide staging and the chmod passes concurrently, and `dist.complete` hashes the git-indexed source in size-bounded batches (`planSourceReadBatches`: 32 MiB / 64 rows per batch; the digest is still computed in index order, so it is byte-identical to the old sequential walk). Measured on one Apple-silicon workstation (a single-host figure, not a bound): `npm run build:production` 8.5 s to about 4.5 s.

Each rule below says what holds it. Where a test goes red when the rule is broken, the bullet names that test; where a rule rests on reading the code or on a later gate, the bullet says so and the rule is not claimed as pinned:

- **`settleAll`, never `Promise.all`, for any fan-out that writes under the staging directory** (`scripts/lib/build-concurrency.mjs`). `Promise.all` rejects on the first failure while its siblings keep writing, and the failure path then removes staging underneath them: the cleanup fails with ENOTEMPTY and that FATAL replaces the real cause, or a sibling recreates a file in a directory the rollback believes is gone. `settleAll` waits for every task to settle, rethrows the first rejection in declaration order (so the reported cause does not depend on a race) and reports later rejections to stderr. Read-only fan-outs may keep `Promise.all`. Pinned by `tests/build-concurrency.test.ts` (the helper) and `tests/build-parallel-discipline.test.ts` (an AST scan of `build.mjs` and `scripts/package-archive.mjs`).
- **Pyodide is staged in two phases.** Every digest is verified first and only then are the files copied, so a bad file leaves nothing half-staged. The verify-to-copy window is whole-set rather than per-file now; the later `dist.complete` and `scan-shipped` gates still cover the final bytes, and exploiting the window needs write access to the repository. The phase order and admission mismatch error (`pyodide runtime admission mismatch`) are pinned by `tests/build-pyodide-staging.test.ts` (reproduction/mutation drill proves a single-pass collapse goes red) and an AST pin in `tests/build-parallel-discipline.test.ts` (`chrome-agent-platform-z3983`); the missing-hash branch (`has no admission hash`) remains unpinned.
- **The source authority is two-stage.** Every indexed row is `lstat`-validated before any read, then read in byte-budgeted batches. `tests/dist-complete-source-authority.test.ts` pins the digest against an independent reference over every batching path, the per-file and aggregate bounds, the planner's memory bound, and that a precomputed `source` handed to the marker writer is a shortcut and never a trust input (`validateDistCompleteMarker` recomputes from disk).
- **Version-GC grace.** After the atomic `dist` pointer swap, `build.mjs` waits before deleting the old versions so a reader that resolved the previous link mid-open can finish. That wait was a fixed 2000 ms whenever an old version was being collected (about half of a warm build). It is now **1000 ms**, and unlike the 50 ms it replaces that number is MEASURED (`chrome-agent-platform-b0ld8`): the slowest reader in this repo hashes the whole built tree (28 files, 19,622,953 bytes), which takes 130-300 ms on an 8-core Linux box, and a paced-reader sweep over a real mirrored tree (`cap-evidence/b0ld8-gc-grace-harness.mjs`, results recorded on the bead) measured it in two conditions: UNLOADED, the full-tree hash lost the tree 6/6 times at 50 ms AND at 100 ms and never at 200 ms (copy-tree survived at 100 ms, single-file at 0 ms); LOADED with six busy children on eight cores, it was still 6/6 at 100 ms and 2/6 at 200 ms, clearing only at 500 ms. 1000 ms is thus 2x the smallest grace that survived a LOADED measurement, and still half the old fixed 2000 ms. It costs roughly 1 s of a ~5 s warm build; a budget that cannot afford that should set the variable explicitly rather than have the default be unmeasured. Tunable with `CAP_BUILD_GC_GRACE_MS=<ms>`. When `dist-versions` holds no prior version (only the live pointer, or residue that is not a version target: dangling symlinks, `.DS_Store`, `._*` metadata) there is no old target for a reader to race and the wait is skipped outright, whatever the setting; that skip came from a second lane on the same bead (`fleet/jjsz-speed-slice`, commit `8bbeb209`, merged to `main` by `5e6d9702`) and is kept, merged with the configurable grace. Only a plain run of decimal digits is a number: `2000` restores the old behaviour, `0` removes the wait, anything above 60000 is capped (a finite value of any length, `1` followed by 308 zeros included), and every other spelling falls back to the 1000 ms default (never to "no grace"): empty, negative or signed (`-0`, `+5`), fractional, exponent (`1e3`), hex/octal/binary (`0x10`), words, units, and a number too large for a double (`Number(raw)` is `Infinity`, from about 1.8e308: `1` followed by 309 zeros). The overflow is a property of the VALUE, not of a digit count. The tradeoff is chosen, not free: a reader that opened a path through the OLD link and is still reading it more than 1000 ms after the swap can see a missing file, where the 2 s window made that less likely but never impossible — the measurement is what moved that from a guess to a number. No test or script in this repository depends on the 2 s window (searched). The 50 ms default had no measured basis; `chrome-agent-platform-b0ld8` supplied one and raised the default to 1000 ms, and `tests/build-concurrency.test.ts` now also asserts the PROPERTY in both directions (a paced reader that pinned the old version dir survives a publish+GC when the grace outlasts it, and is torn down when it does not), so the value cannot be lowered into unsafe territory without a red test. The policy is `resolveGcGraceMs`, pinned by `tests/build-concurrency.test.ts`.
- **`scan-shipped` reads in batches.** `scripts/scan-shipped.mjs` merges its two AST walks (the sink aliases and the script-element bindings) into one pass, reads files in batches of 32 and scans the bundled Wasm concurrently. Two reviewers argued the merged walk is behaviour-preserving by reading it, including the assignment-operator handling and walk order; the evidence is `tests/scan-shipped.test.ts` and the schema-aware Wasm test in `tests/wasm-package-authority-static.test.ts` (split out of `tests/wasm-package-authority.test.ts` by chrome-agent-platform-uvo3 so the tracked-source walk is always-on), not a before/after oracle.
- **The Zod `Doc` scrub has a fast path.** `scripts/lib/scrub-zod-doc.mjs` returns a bundle unchanged, and unparsed, when it contains no `Doc` / `Doc<digits>` token. The one known limit is an escaped spelling of the class name (`class \u0044oc`), which carries no such token, so the fast path does not scrub it. esbuild never emits that spelling, and the final whole-AST `assertNoDynamicEvaluators` gate that `build.mjs` runs over every published bundle is the backstop. `tests/scrub-zod-doc.test.ts` pins the fast path (byte-identical output for token-free input, a real `Doc.compile` shape still scrubbed) and asserts the current escaped-name behaviour so that a change to it is a conscious one.

### 6.2 The build-once record

On a successful **store** build, `build.mjs` writes `<durable root>/serial-build-once/<commit>-<source-digest>-<dist-complete-content-hash>.json` (`{ code: 0, stdout, at }`) so a later serial test file can reuse that build's output instead of paying for another build. The final hash covers the exact validated marker bytes, including generated bundle hashes: two builds of one indexed source that produce different output cannot reuse each other's stdout. The reader still validates the live marker before trusting a record; the key is not a substitute for that check. The record says "this build exited 0", so:

- It is written **after the last fatal step** (staging cleanup, gallery sync, lock release) by the only writer `build.mjs` uses, `writeBuildOnceRecord` in `scripts/lib/build-once-record.mjs` (the test fixture `tests/fixtures/build-once.mjs` writes a record itself when it has to run a build: a second writer, outside `build.mjs`), which applies the strict gate `shouldRecordBuild({ buildSucceeded, exitCode })` **itself**, so the call site cannot weaken it. A build that dies in a finalizer, or exits non-zero for any reason, records nothing. A refused call touches nothing on disk (not even the directory), the key must be one safe path segment (no `../`, no `/`), and a write failure is non-fatal cache population (`{ written: false, reason: "write-failed" }`, never a throw). The behaviour is pinned by EXECUTION in `tests/build-once-record.test.ts` (a table over record × `buildSucceeded` × `exitCode` against real files, judged by an oracle that does not import the gate), and the call site by `tests/build-parallel-discipline.test.ts` rule B (an AST pin: exactly one awaited top-level call after the last top-level `try`, its exact arguments, nothing fatal after it, and no second writer or record-directory literal anywhere in `build.mjs`). What those pins do not catch, stated in their headers: a fatal raised from an exit handler or an unhandled rejection after the call, and a writer that assembles the directory name at runtime. Also unpinned: what is CAPTURED (`storeBuildRecord = { key, stdout }`): a wrong key field or a blank `stdout` keeps every test green, and `build-smoke` asserts only the exit code of the reused record (`chrome-agent-platform-l3dc2`).

### 6.3a The journey watchdog covers two phases and now says which (qifg4)

The harness arms one 90 s watchdog at `main()` entry, so a run that has not completed an assertion within 90 s
exits 124 with a frontier named. That budget covers two different phases, and they must not be confused:

- **pre-connect** - profile/evidence setup, the browser launch, the DevTools endpoint fetch and the CDP websocket
  open. The launch (including the serialized-Chrome queue, whose own wait is `CAP_CHROME_LOCK_WAIT_MS`, 20 min
  default) is deliberately **excluded** from this budget: `beginLaunchAdmission()` suspends the watchdog and
  `endLaunchAdmission()` restarts it once the browser is live, because admission has its own bounded verdict
  (exit 75 + the load numbers) and legitimately outlasts 90 s. That bracket is pinned by `cec16` in
  `tests/journey-abnormal-exit-frontier.test.ts`.
- **assertion** - every check after the connect, named by the frontier.

What the budget still covers pre-connect was measured rather than assumed: on this box, the real harness with
`CAP_JOURNEY_STOP_AFTER` at "extension loaded" reaches a passing first check **6.0 s** after process start, about
7% of the budget, and the browser's own endpoint wait is hard-bounded at 20 s by the launcher.

The defect qifg4 names is therefore **not** the bound - it is the message. Before the first check nothing has
COMPLETED, and the timeout attributed the hang to a check: `frontier check: "<the next expected check>"`, i.e. it
named work that had not started as the thing that hung. `startupPhase` now records which pre-connect step owns the
armed watchdog - setup, then the DevTools endpoint wait, then the websocket open - and while it is set the message
says `Hang detected during STARTUP phase "..." - no check had started yet (next expected: ..., last completed:
...)`. It is cleared when the connect completes and whenever a check takes the frontier.

**The first attempt at this was dead code, and the real run found it** (worth recording because the unit pin did
not): the branch was guarded by `lastStartedCheck === null`, but the module seeds `lastStartedCheck` with
`EXPECTED[0]` at load time, so it is never null in the real script - the phase branch could only be reached from a
fake harness. `CAP_JOURNEY_WATCHDOG_MS=1 deno run -A scripts/chrome-journeys.ts` printed the OLD message and proved
it. The phase now takes precedence on its own, and the unit harness seeds the frontier exactly as production does,
so the same mistake cannot pass again.

Bounds are unchanged on purpose: a separate startup bound would duplicate the launcher's endpoint wait and the
admission's exit-75 verdict, and would false-trip a legitimate serialized-lock queue. Pinned by the `qifg4` tests,
and demonstrable for real with `CAP_JOURNEY_WATCHDOG_MS=1 deno run -A scripts/chrome-journeys.ts` (exits 124 with
the STARTUP message above).

### 6.4 What is not proven, and the residual risks (each is a bead)

This is what the jjsz landing does **not** establish. None of it is a known failing gate; each item is a place where a gate could be weaker than it reads, or where a deliberate trade was made.

**Linux qualification (`chrome-agent-platform-mwj7v`).** The original jjsz landing was gated only on macOS arm64 (Deno 2.9.0), but later Linux gates now execute the seam-driven macOS branches and the real-process `ps`/`flock` probes. A Linux fast gate on `cd89df5f5` ran `jjsz-macos-custody-ps.test.ts`'s real `ps` identity, absent-pid, child-table and detached-leader assertions; it reported the one intentional jjsz ignore in `jjsz-macos-quiet-window.test.ts`: the **real no-`/proc` hostile-locale `ps` walk** exists only on hosts without `/proc`. Its fake-`ps` verdict tests execute on every platform; that real no-`/proc` test remains macOS-only and is **not** a Linux pass. The weaker macOS SID proof is separately tracked by `chrome-agent-platform-xjjhi`. The Linux `/proc` SID refusal now also has a real process-group leader that did not start a new session, with an independent `ps` oracle (`tests/jjsz-macos-custody-ps.test.ts`). Host/tool preconditions for the remaining real probes are measured through raw tool probes, not the code under test; a missing required `perl`, `pkill`, `pgrep` or `setsid` still fails rather than silently skipping (§6.3). The merger owns the full Linux `npm test` verdict, including its **ignored** count; focused or fast runs alone do not supply that union verdict.

**macOS custody proofs are weaker than their Linux counterparts, by construction** (`chrome-agent-platform-xjjhi`):
- `ps` cannot report a session id, so a macOS identity carries `sid` = `pgid`; the `sid === pid` half of the "launched leader" check is implied by `pgid === pid` and proves nothing there. A portable signal exists (`ps -o stat=` carries `s` for a session leader) and is not wired.
- The inherited canonical-lock proof is "the file behind fd 9 has the lock file's device and inode, **and** `flock -n` cannot take the lock". That proves someone holds the lock, not that fd 9 itself does (macOS has no `/proc/self/fdinfo`). `flock` is resolved through `PATH`, as `scripts/security-suite-supervisor.sh` resolves the `flock` that takes the lock in the first place.
- **That macOS branch is reached only through seam tests today.** `npm run test:security` cannot start on macOS, on `main` or on this branch: the Deno runner's `node:fs` `fstatSync(9)` on an inherited descriptor throws `EBADF` (Deno's descriptor namespace is not the OS table; Node reads the same descriptor fine), so the runner refuses with "canonical inherited lock fd is missing" before the macOS proof can run. `main`'s `/proc`-only check refuses identically. The real supervisor flow was therefore never measured on macOS, and no Linux host was available either (`chrome-agent-platform-mwj7v`). `chrome-agent-platform-8bp69` records the measured fix direction: open `/dev/fd/9` write-only and `fstat` the handle (`stat("/dev/fd/N")` is not equivalent).

**Lifeline edge cases, decided (`chrome-agent-platform-4o93n`).** Three cases were found and deliberately left
alone during jjsz. Each now has a decision rather than an open question:

- **(c) A `pkill` pattern rejection is unreportable once the parent is dead.** Accepted, no change. The pattern
  is built by `lifelineMatchPattern`, which escapes every ERE metacharacter and anchors the end, so a rejection
  cannot come from a caller-supplied profile any more — it would need a mangled pattern between construction and
  execution, or a `pkill`/libc that refuses the ERE. The group kill has already run by then, and the only thing
  lost is ATTRIBUTION: the watcher exits 3 into a pipe nobody is reading. A durable receipt written from that
  dying shell would be a new failure mode in the teardown path to report a case the escaping already prevents,
  so the trade is recorded here instead. The positive half is pinned: a rejection that IS observed keeps the
  lifeline ARMED rather than disarming (`tests/jjsz-lifeline-leader-exit.test.ts`, seam `signal`).
- **(d) A handle-less teardown could not serialise with a sweep for its profile — FIXED.** The serialising state
  hung off the `Deno.ChildProcess`, and `teardownChrome(null, profile)` has no handle, so it ran straight into an
  in-flight sweep for the same profile; the sweep's `pkill -9 -f` matches the teardown's own `pkill`/`pgrep`
  command lines and SIGKILLs them (exit 137), failing the teardown. `killProcessTree` now waits for every sweep
  on that PROFILE that has left `armed` to settle before it signals anything, which is the same key the sweep
  registry already uses. Pinned by `tests/jjsz-lifeline-runner-exit.test.ts` "4o93n (d)": with the wait removed,
  the teardown's `pkill` fires while the sweep's watcher is still running (red), and with it the teardown starts
  only after the sweep settles. A wait alone was not enough (review finding `vy15c`): a sweep that ends
  **UNCONFIRMED** still let the teardown resolve, and a resolved teardown reads as "the profile is clear". The
  reap now runs anyway - best effort is the point of a teardown - and then the call THROWS naming the profile
  and the UNCONFIRMED verdict, so the caller never receives a clean it cannot prove. Pinned by
  `tests/jjsz-lifeline-leader-exit.test.ts` "vy15c".
- **(e) Another PROCESS's `pkill`/`pgrep` on the same profile can be SIGKILLed by the sweep.** Accepted, no
  change: it fails closed (the teardown throws, the supervisor sidecar names the residue). Serialising across
  processes needs an OS-level lock held for the sweep window and taken by every cleanup path, including the
  third-party ones this repo does not own — a heavier mechanism than the P4 risk justifies, and one that would
  put a lock acquisition in the path whose job is to run when a process is already dying.

**Unreadable custody observations fail closed** (`chrome-agent-platform-yuu9s`): the supervisor keeps sampling after a process-table failure, but an unverified final sample (or an earlier failure while its observed set was empty) exits 70 with a named receipt reason rather than reporting a clean run. Verified residue rows keep their existing receipt shape; unverified rows carry `unverified` and `unverifiedReason`. Linux `/proc` listing and per-pid non-ENOENT read failures now reject as unreadable; only an ENOENT for a vanished process is clean. Strict per-pid checks can refuse a security run on a host whose `/proc` hides unrelated processes (`hidepid`); that is an explicit fail-closed cost, not evidence that residue is absent. Abrupt supervisor death before receipt writing remains outside this custody guarantee.

**Probes that are not fully bounded** (`chrome-agent-platform-d9fyo`): custody's `ps` has a 5 s timeout but runs under the inherited environment; the `flock` probe has no timeout; the quiet-window sampler's `ps` has its environment pinned but no timeout.

**Deliberate fail-closed choices with an operator-visible cost, and how each was decided** (`chrome-agent-platform-qo3u8`, decided 2026-10-17):
- **Retry, keep the verdict.** A transient `ps` failure at custody's final residue check used to exit 70 on its own. The read is now attempted a bounded 3 times, 100 ms apart, before an unreadable observation is declared unverified: one hiccup no longer fails a security-suite run, and a persistent failure still exits 70 with the same named `observation-unverified` reason, so the fail-closed direction is unchanged. A `gone` verdict is an answer, not a failure, and is never retried. Cost: up to about 200 ms per unreadable descendant, on the failing path only.
- **A start we cannot PLACE is UNKNOWN, not DIFFERENT — and shape is not proof of place.** A live build-lock owner recorded before the `PS_ENV` pin holds a `start` the canonical reader could not compare, so it read as a different process and the lock was stealable once, at the upgrade. The owner file now records **provenance** (`startBasis`) alongside the value: kernel ticks (`/proc/<pid>/stat` field 22, environment-free) always compare, and `ps` text compares only under the current marker (`ps-lstart-utc-v1`). A lock written before that field exists carries no marker, so its start is UNKNOWN and the holder stays alive; after one upgrade every new lock is marked and comparisons resume. Comparable values still prove pid reuse exactly as before, and a persistently broken `ps` still refuses acquisition (bounded, about 24 s) rather than stealing.
  - **The refusal is TYPED, and it no longer calls an undecidable owner a live one** (`chrome-agent-platform-khkqz`, the
    residual after the provenance fix). `lockOwnerVerdict()` reports *why* a lock was kept alive, and an exhausted
    `acquireBuildLock` throws an error carrying that `reason` and a `code`: an owner whose recorded start cannot be
    PLACED (reason `start-basis-unknown`, or `probe-start-uncomparable` when the live probe is the unplaceable side)
    fails closed as `LOCK_OWNER_PROVENANCE_UNKNOWN` and names the deliberate removal as the remedy, because the pid in
    the file may since have been reused by an unrelated process and killing it would be wrong advice; a holder that
    was PROVEN alive keeps `LOCK_HOLDER_ALIVE` and the original "another LIVE build" wording. `holderIsDead()` remains
    the yes/no form of the same decision, branch for branch. A lock with no recorded start at all (a writer whose own
    identity read failed, jjsz) keeps the proven-live path and its wording.
  - **Why provenance and not the string shape** (review finding `chrome-agent-platform-khkqz`): the pre-pin writer did not pin the time zone, so the same live macOS process recorded as `Wed Oct 7 13:10:01 2026` under a C locale in Europe/London and reads now as `Wed Oct 7 12:10:01 2026` under `PS_ENV` (TZ=UTC). Both have the canonical shape, so a shape rule compares them and reads pid reuse — the one-time steal returns. Non-C locale text (`Wed  7 Oct 12:10:01 2026`, `Mer  7 oct ...`) was only the easy half, and the first version of this change covered only that half; the reviewer reproduced the leak against it.
- Both decisions are pinned by seam tests in `tests/qo3u8-fail-closed-tradeoffs.test.ts` (9 cases). The falsifier is a mutant that KEEPS the new seams and restores only the old decision: restoring the single-attempt read turns exactly the 3 retry/decision pins red (4 of 7 pass in both states), and restoring the shape-only start compare turns exactly the 2 provenance pins red (7 of 9 pass in both states). So neither decision — nor the provenance gate — can revert silently. The retry budget (`RESIDUE_READ_ATTEMPTS`, `RESIDUE_READ_RETRY_MS`, pinned as values) and the basis constants (`PROC_START_BASIS`, `PS_START_BASIS`) are pinned rather than inferred.

**The crash lifeline: policy, cost and limits** (`attachProcessLifeline`, section 3). These are the places where it is weaker than it reads; every one fails closed or needs a second failure on top of the first.
- *Policy: an unprotected launch is a warning, not a refusal.* If the watcher cannot be started (no `/usr/bin/perl`, `EAGAIN`), `launchChrome` writes one line to stderr and goes on with the pre-jjsz exposure. Refusing the launch instead would hard-fail every acceptance script on a host with a missing `perl` or a transient fork failure, for a protection that only matters when the launcher is killed. Whether to flip this is recorded with the other fail-closed trade-offs (`chrome-agent-platform-qo3u8`).
- *Cost:* a normal `teardownChrome` is about 40 ms slower than before (the bounded `ps` wrapper); a teardown after a leader-only kill is 85 to 120 ms slower, because it waits for the sweep (medians 138 to 144 ms before, 224 to 265 ms after). Both measured with real Chrome for Testing on one host.
- *No leader-identity re-check.* The watcher signals the group by number. A live group is always the right one, but an EMPTY group whose pid was recycled, with the launcher killed inside that window, would be signalled (`chrome-agent-platform-lsk1p`).
- *Isolation window.* The watcher's own `setsid` runs a few milliseconds after the spawn returns. A kill of the launcher's whole process GROUP inside that window takes the watcher with it (7 of 20 trials orphaned the target before isolation was visible; 20 of 20 were reaped after) (`chrome-agent-platform-6tau8`).
- *`launchChrome` failure path.* If `teardownChrome` throws inside the catch around `isolatedProcessGroup`/`attachProcessLifeline`, the launch lock and fleet lease are not released and the original error is masked; an unreadable table at launch also leaves the cleanup without a recorded group (`chrome-agent-platform-5fh6a`).
- *Three edges, deliberately unchanged* (`chrome-agent-platform-4o93n`): a `pkill` pattern rejection cannot be reported once the launcher is dead (the group kill still ran); a `teardownChrome(null, profile)` with no process handle cannot serialise with an in-flight sweep, so the sweep can kill that teardown's own `pkill`/`pgrep` and the teardown then throws (fails closed); and a concurrent `pkill`/`pgrep` of the same profile run by another process can be killed the same way.
- *A launcher that kills only the leader must wait for the sweep* (found by the round-2 security review; the leader-exit SWEEP is new with the jjsz work: `origin/main`'s lifeline is disarmed the moment its leader exits, `proc.status.then(disarm, disarm)`, so it never sweeps and nothing lingers). The watcher lingers about 110 ms after a leader exit (`kill -TERM; sleep 0.1; kill -KILL; pkill`). `scripts/security-suite.ts` used to exit straight after `await chrome.proc.status`; the real supervisor (`scripts/security-suite-supervisor.mjs`) takes a final `observeDescendants` sample after the runner exits and then judges `liveObservedResidue` (`scripts/security-suite-custody.mjs`), so a watcher still alive at that sample reads as `descendant-residue` and exits 70 (expected; neither frequency was measured). The same lingering sweep can also `pkill` a second browser opened on the same profile, and that one WAS measured. `reapLeaderAndSettle` (`scripts/lib/reap-leader.ts`) kills the leader, awaits its exit and then awaits the lifeline's `settled` promise; four scripts call it: `scripts/security-suite.ts`, `scripts/page-actions-journey.ts`, `scripts/keyless-first-result.ts` and `scripts/security-injection.ts`. **The fourth was missed by the first scan and found by the round-3 security review:** `security-injection.ts` has ONE `launchChrome(` call site, inside a `boot()` that runs twice; it killed the first browser with a bare kill and booted a second on the same profile with no pause. Measured on the real script (Chrome for Testing 149, macOS arm64, built trees, an empty slot directory per run, 3 runs each; the oracle is "the second boot reached the checks", not the script's own pass/fail, which is red on macOS on `main` for an unrelated reason: Chrome for Testing drops the seeded Preferences grants): the second browser came up in 0 of 3 runs at the unfixed tip (two "Chrome never printed a DevTools endpoint", one EPERM out of the killed launch's own teardown), came up in 3 of 3 on `origin/main`, and in 3 of 3 with the helper, with no stray Chrome afterwards (evidence bundle `real-chrome-injection/`). **What this rests on:** a deterministic fixture judged by the REAL `observeDescendants` and `liveObservedResidue` (`tests/jjsz-lifeline-runner-exit.test.ts`: a positive control that reproduces the old shape, behavioural tests of the helper, and per-site AST pins each checked against in-file mutants, plus a binding pin that the four scripts import the helper under its own name from the one module and declare that name, or its numbered form, nowhere else: a drill that deleted the import and kept the call survived every call-site pin until it was added; the helper tests are time-bounded, so a helper that stops killing goes red in 15 s instead of hanging). The two cross-process negative windows ("the runner has not reaped yet", "no second browser has opened yet") are counted on the runner's own heartbeat after an in-stream `LEADER_EXITED` marker (`tests/fixtures/jjsz-lifeline-runner.ts`), not on a sleep in the test, so a starved runner cannot pass them for the wrong reason. It is not the real flow: that cannot run on macOS (the lock-proof note above, `chrome-agent-platform-8bp69`) and Linux is unverified (`chrome-agent-platform-mwj7v`). **The residue pins remain per-site, but same-process relaunches through `launchChrome` now await a fired profile sweep** (`chrome-agent-platform-80yqb`): the first scan that said "none relaunches on the same profile" missed one (`security-injection.ts`, whose single `launchChrome(` call site runs twice). About 30 other scripts still do a bare `proc.kill`; the widened round-3 scan found no further same-profile relauncher among them (`perf-seeded-scale`, `read-page-host-grant-acceptance` and `screenshot-vision-evidence` end with a bare kill and, on the reviewer's reading, nothing judges or relaunches after them; not drilled), but nothing would go red if a new one appeared (`chrome-agent-platform-6efbv`). The `80yqb` registry waits only for a fired, in-process same-profile sweep before `launchChrome` spawns; it never waits for a live browser. **That wait is bounded on both sides since `chrome-agent-platform-t5o2i.2`:** the 5 s sweep bound SIGKILLs a watcher that overran, and the waits that FOLLOW it (the SIGKILLed watcher's own exit, and its stdin close) now have their own short bound (`LIFELINE_SETTLE_WAIT_MS`, 1000 ms, `lifeline.deps.settleTimeoutMs` in tests) instead of awaiting a promise that a watcher stuck in uninterruptible I/O may never settle. A watcher that outlives BOTH bounds ends the transition honestly UNCONFIRMED: `lifelineState(proc).cleanupConfirmed` is `false`, one stderr line says the watcher (and any `pkill` it already forked) may still signal the profile, and — because that is a false clean, not a clean sweep — the registry keeps the entry and a same-profile launch through `awaitFiredLifelineSweep` REFUSES with a fresh-profile instruction rather than racing it. The registry entry is keyed on a lifeline having LEFT `armed`, so a same-profile launch also WAITS for a DISARM that is still in flight (v8zbu/rm08r: keying on `fired` alone let a launch run past the very quarantine this guard exists for, while a disarm's watcher exit was unproven), and a merely armed leader is still never awaited. The watcher's EXIT is the deciding signal, not the close: an unsettled `stdin.close` (the sweep trigger) is reported on its own line but does not clear `cleanupConfirmed` and does not refuse anything, because a close call that has not returned says nothing about whether a process is still alive. A confirmed sweep behaves exactly as before (entry removed, relaunch waits and proceeds). The three falsification pins are in `tests/jjsz-lifeline-leader-exit.test.ts` (`uninterruptible` fake watcher for the sweep and the disarm, plus a close-only overrun that must NOT refuse), with the anti-vacuity partner asserting a watcher that DID exit on SIGKILL is confirmed. The sweep shell is unchanged, so helpers are still reaped, but cross-process and parent-death relaunches cannot consult this registry (`chrome-agent-platform-6n41t`), and direct spawns outside `launchChrome` remain unguarded. The helper still protects the four named runners' supervisor-residue verdicts. The pins' own known survivors (a second top-level `try`/`finally`, which the first-match `find` does not read; a write to the launch result through a member; a late or dead store of `proc = l.proc`; a `throw` or a `Deno.exit` ahead of the finalizer's awaited `kill()` (a top-level `return` is a SyntaxError in a module); bare-kill spellings the dotted-name rule does not read; a rebinding of `kill`; a literal `Deno.remove(` call that is not the profile removal, which satisfies the order rule by itself (a finalizer with no literal `Deno.remove(` at all is rejected: "update this pin")) are listed in `chrome-agent-platform-t5o2i`; the plain, compound, destructuring (array, object and rest), `++`/`--` and for-in/of writes of the handle are rejected, and the guard test of the `if (proc)` reap and the `await` test that every pin reads its statements through each have a mutant that only they reject (round 7; the clause-by-clause claim is about the clauses the reviews named, not a proof that none is left).

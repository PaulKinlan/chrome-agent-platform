# Script-registration API shapes (nim1; non-security investigation)

**Status:** Chrome API contract documented; product shape and owner approval boundary unresolved. This is not a finding that model-authored source ran in a page origin. `chrome-agent-platform-jbsi` tracks that separate, unproven security claim.

| Tool pair | Current `extension/lib/browser-tools.js` call | Chrome API `js` shape |
| --- | --- | --- |
| `register_user_script` / `update_user_script` | `chrome.userScripts.register/update([{ id, js: "<source>", matches }])` | `RegisteredUserScript.js` is a nonempty `ScriptSource[]` on register (optional on update); inline source is `js: [{ code: "<source>" }]`, or a packaged extension-relative file is `js: [{ file: "content/bridge-auth.js" }]`. Each item specifies **exactly one** of `code` and `file`. |
| `register_content_script` / `update_content_script` | `chrome.scripting.registerContentScripts/updateContentScripts([{ id, js: "<source>", matches }])` | `RegisteredContentScript.js` is a `string[]` of JavaScript **file paths**, e.g. `js: ["content/bridge-auth.js"]`. No `code` alternative is declared for this registration API. Registration validates files. These are extension-relative packaged filenames, **not** inline source strings or a single string. |

Sources: [Chrome `userScripts` API](https://developer.chrome.com/docs/extensions/reference/api/userScripts) (`RegisteredUserScript`, `ScriptSource`); [Chrome `scripting` API](https://developer.chrome.com/docs/extensions/reference/api/scripting) (`RegisteredContentScript`, registration file validation). The package-relative reading of `scripting` paths follows its file-path type and file-validation semantics; exact rejection strings require a correctly authorized real-Chrome probe. `extension/lib/enrollment.js` already registers packaged scripting files via `js: [BRIDGE_AUTH_JS, MAIN_WORLD_JS]` as a product-side structural example.

`tests/chrome-tools-t12.test.ts` now rejects the current raw strings at all four in-memory mutation boundaries. Its `[T12 schema fake, NOT Chrome]` errors are deliberately **fake-derived**, not Chrome errors. A positive validator control for `[{ code }]` checks only shape and **does not register or execute** that source. The test checks that existing registrations stay unchanged after invalid updates and that the no-permission/no-grant refusals still occur before any Chrome call. Before adding the strict fake, the focused file passed 23/23 with permissive mocks; retaining the original success assertions after adding it produced RED 20 pass/3 fail against current product bytes (`/tmp/j5yz-nim1-strict-red.log` on the j5yz VM). The checked-in test asserts the honest rejection, so it can be GREEN without pretending product registration works.

**Owner decision required before product changes:** The project coordinator and owner must decide whether `userScripts` should allow inline model-authored code with a digest-bound owner approval, restrict it to packaged files, or remove that tool; and whether content-script registration should accept only known packaged filenames or remove the source-taking tools. Do not repair the raw string to `[{ code }]` by itself: that would newly make inline model-authored source executable. Do not use a permissive mock to restore a success assertion. The `list_user_scripts` preview/byte count also assumes a raw string, while `list_content_scripts` currently counts filename characters as bytes; settle their response contracts together with the product decision.

A future authorized real-browser test must verify actual API rejection and valid controls in a correctly privileged extension context. Permission or user-toggle refusal, a queue timeout, and a wrong-page `chrome is not defined` error are **not** a verdict about page-origin execution. No such real-browser result is claimed here.

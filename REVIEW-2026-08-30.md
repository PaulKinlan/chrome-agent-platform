Reading the source confirms the security architecture is real, not claimed: sender-derived authority (origin, tab and document ids come from the browser-attested sender, never the message body), an HMAC'd page-to-extension bridge with an out-of-band nonce, origin-keyed OPFS memory the model can never address by origin, generated HTML behind a double opaque iframe with `connect-src 'none'` that held against a seven-way leak probe, approval tuples that are single-use, TTL-bound, payload-digest-bound and frozen to the model principal, and provider keys that never appear in logs, receipts or diagnostics.

**Conclusion: the mechanics are sound. The demo fails today on gating, on what the transcript keeps, and on the first screen** — none of which is a tool, a model or a security boundary.

## 2. The thesis, and whether the build proves it

**Thesis:** Chrome itself can be the agent runtime — an agent that lives in the browser can run your tabs and use any site's own tools (WebMCP), with the browser's origin isolation and permission model keeping it honest; no cloud browser, no screenshot-and-click.

**Does the build prove it? Half.**

- **Sites as tools — proven.** The WebMCP path is the strongest thing in the product and the one thing no comparator does: passive detection reports a tool count within 3 s, the picker names the exact tab, enrollment and per-tool first-run approval are real, invocation mutates the page. It is not demonstrable in sixty seconds because the only origin with tools is a fixture on 127.0.0.1 and the entry is a link inside a card.
- **Run your tabs — proven for browser chrome, not for pages.** Forty-plus browser tools drove real side effects on the first try once the gates were aligned. There is no click, type, fill, scroll or find-element tool of any kind; the only way to act inside a page is a site that ships WebMCP tools. "Log in to X and add Y to the cart" is impossible today on a site that has not adopted WebMCP.
- **Keeps it honest — architecturally strong, narrated inconsistently, and inverted relative to the pitch.** The layers where a hostile page attacks the extension are hardened to an unusual degree. The layer where a hostile page attacks the user through the model has no fencing, no policy text, standing grants instead of per-action approvals, and one tool pair that forms an unapproved fetch channel. The install asks for `<all_urls>` while the README says it does not.
- **The first five minutes prove nothing to a person without a key.** The default provider replies with the size of the system prompt.

The product has two thesis statements — "sites as sub-agents" (unique, working, hidden) and "a coworking environment for knowledge workers" (aspirational, missing page actions and a companion) — and the hub serves neither: it is a third thing, an agent-management dashboard. Q20 in `docs/OPEN-QUESTIONS.md` asks the owner which comes first.

## 3. Ten findings leadership must hear

Ranked by how early a person hits them. Each is a tracker entry.

1. **Tool gating deadlocks itself.** Four independent gates stand between the model and `tabs.create` (Chrome permission, browser-control grant, single-driver lease, run fence) and only the last two are consistent. The Settings toggle that grants browser control acquires a 15-minute `interactive` lease it never releases, so the next hub run is told "another surface is driving the browser"; while an agent holds the lease the owner cannot revoke browser control, and the switch renders off while the grant stays on. This is the whole story of "open tab does not open a tab": the tools execute, the gates deny. → `CAP-FB-20260830-BROWSER-LEASE-DEADLOCK-01` (P0)
2. **Denials never become grant cards.** A fresh install needs three separate owner actions before `open_tab` can succeed and none is requested in context. The tab tools return a legacy denial shape the conversation's normaliser drops, so the error text says "enable it from the chat when prompted" and nothing prompts. The approval-card machinery exists and works for a different subset of tools. → `CAP-FB-20260830-DENIAL-TO-GRANT-CARD-01` (P0)
3. **The answer is replaced by boilerplate and clipped to 240 characters.** On every real provider the model's real reply ("Here are your open tabs: …") is visible for about three seconds, then agent-do's synthetic "Continue working" nudge produces "Here's a summary of what I've done" and on re-render the real answer is gone. Only the terminal step's text is persisted, and the back-fill commits the 240-character `terminal.summary` as the thread's message — a 4,540-character answer survived as 299 characters ending in an ellipsis. Permanent. → `CAP-FB-20260830-TRANSCRIPT-FULL-ANSWER-01` (P0)
4. **There are no page-action tools.** Every comparator leads with "it fills the form / clicks the button". Either add a minimal grant-gated family on `chrome.scripting` behind the fencing and ledger below, or decide in writing that the product is WebMCP-only for page interaction and put it on the slide. → `CAP-FB-20260830-PAGE-ACTION-TOOLS-01` (P0, owner question Q19)
5. **`create_script` + `run_script` is an unapproved fetch channel.** Neither is in `DESTRUCTIVE_ACTIONS`; the sandboxed script's `fetch` is bridged to the service worker, which accepts any http(s) URL including loopback and private ranges (it holds `<all_urls>`) and returns up to 1 MB to the model with no card. A prompt-injected page can exfiltrate memory or cookie data via the URL alone. Cut `run_script` from the interactive toolset until gated. → `CAP-FB-20260830-RUN-SCRIPT-FETCH-APPROVAL-01` (P0)
6. **Page text reaches the model raw.** `read_page` returns `innerText` verbatim inside the tool result with no boundary and no policy text saying page content is data. The live injection page was refused by both tested models — the platform added no defence in depth, and a compliant model would have closed five tabs with no card. → `CAP-FB-20260830-UNTRUSTED-CONTENT-FENCING-01` (P0)
7. **The first screen.** The composer is the 41st tab stop and entirely below the fold at 1024x700; the first-run card has six actions and its own X; seven empty states stack beneath it; there is no keyless first result. → `CAP-FB-20260827-HUB-FIRST-RUN-01`, `CAP-FB-20260830-KEYLESS-FIRST-RESULT-01` (P0)
8. **Twenty-two phantom agents.** A fresh profile lists 22 disabled recipe templates as agents in the sidebar and the side panel ("Sorting Hat … Schedule off") beside a panel that says "0 agents". Settings was fixed on 08-29; the surface the owner sees first was not. → `CAP-FB-20260830-FRESH-PROFILE-TEMPLATE-AGENTS-01` (P0)
9. **Nothing streams.** The service worker uses `doStream`, chunks arrive, and none are forwarded: assistant text appears in one paint when the step completes. Time-to-first-visible-token equals time-to-complete — 7 to 25 seconds of blank "Thinking…" is the demo's dominant feel. → `CAP-FB-20260830-TRANSCRIPT-STREAMING-01` (P1)
10. **Editing shows no diff.** The `asset.update` approval card reads "Approve asset.update? Target reference: <hash>" — no name, no content, no diff; after approval the only trace is a blank frame rendered from a display-truncated argument string, and no `<artifact-card>` ever renders in a real run although `ARTIFACTS-IN-THREAD-01` is marked DONE. The agent cannot read or write a local file at all. → `CAP-FB-20260830-EDIT-APPROVAL-SHOWS-DIFF-01`, `CAP-FB-20260830-THREAD-ARTIFACT-CARD-01` and the diff chain (P1)

Three things behind several of these: the lazy tool protocol makes correct behaviour depend on the model reading a 19 KB manual and on a single-use ref surviving a schema mistake (`SELECTION-REF-VALIDATE-FIRST-01`, P0; `MODEL-TOOL-ADHERENCE-01`); "bounded for display" strings are reused as data (the blank frame, the envelope leak); and provider setup has three silent-failure paths that all say "ready" until the run (`PROVIDER-ERROR-TRUTH-01`, `PROVIDER-SET-NO-BASEURL-01` raised to P1, `MODEL-FIELD-EMPTY-SAVE-01`).

## 6. The five-minute demo script and its ranked blockers

**Preconditions:** headed Chrome; a valid key already saved (or item 10 landed) and verified on the demo machine an hour before; the showcase WebMCP site open in a tab; two or three real article tabs open; one scheduled agent created ten minutes earlier so it has produced a report.

2. **1:00 — The site is a tool.** Switch to the showcase shop tab; the hub shows "this site offers 4 tools". Ask: *Add the cheapest widget to the cart and tell me the total.* Approve the first tool use once. The page changes; the tool cards name the site's own functions — no screenshots, no guessing. (Needs 18.)
3. **2:15 — Isolation and consent.** Open Settings → Permissions for ten seconds: what was granted, to which origin, and that memory is per-origin. "The site cannot see the agent's memory; the agent cannot touch a site you did not approve." (Needs 19 to be truthful, 16 to be presentable.)
4. **3:00 — It worked while I was away.** Back to the new tab: the timeline shows "Reading digest ran 8 minutes ago — 3 articles summarised — Open" and the artifact opens in a tab. (Needs 26, 28.)
5. **4:00 — Make something.** *Turn those summaries into a one-page brief I can share.* An artifact renders in the thread; open in tab; "this outlives the agent and the task." (Needs `THREAD-ARTIFACT-CARD-01` from 29.)
6. **4:45 — Close.** "Any site that adopts WebMCP joins this without us shipping anything." Show the fixture source: six lines to register a tool.

**Ranked blockers that would embarrass the owner today:**

## 7. What works well (keep)

- **The hub is genuinely fast** — 15-55 ms FCP, composer usable under 60 ms, zero long tasks, zero layout shift, and it stays that way at 120 threads because every list is bounded. This is the single most important number for the demo and it is good.
- **Service worker cold start is healthy** (~115 ms), no top-level await, heap flat across 120 runs.
- **WebMCP end to end is real** and 42/42 — passive detection carrying only a count, exact-tab identity, enrollment, per-tool approval, invocation with a visible side effect, survives reload. Build the pitch on it.
- **Real tool dispatch is solid**: with the gates aligned, 40+ Chrome-API tools drove real side effects on the first try with bounded, secret-redacted results and fail-closed errors for the ungranted cases; management tools (artifacts, scripts, named agents, schedules) all work through the real executor; scheduled agents fire and are durable.
- **The security engineering**: no `eval`/`new Function` in any shipped bundle; all 59 audited `innerHTML` sinks are static or escaped; the sandbox held against a seven-way leak probe; sender-derived authority; HMAC'd bridge with replay counters; origin-keyed OPFS via injective encoding; single-use digest-bound approval tuples frozen to the model principal with genuine-gesture checks on both approval UIs; key hygiene end to end (write-only input, redacted reads, diagnostics scrubber). Both tested models refused the visible-text injection.
- **The token system** in `extension/shared/theme.css` — `light-dark()` per token, warm neutrals, one accent; a contrast walk over six surfaces in both schemes found exactly one AA failure. `prefers-reduced-motion` leaves zero animations. Landmarks are real; every hub control has an accessible name; the conversation is a polite `role=log`.
- **The `+` menu, `<agent-picker>`, the `@` mention popover and `confirmActionDialog`** are one component each, used everywhere; the create-agent dialog after DECLUTTER and REPAIR is the best-composed dialog in the product; the sidebar rail collapse is clean.
- **Composer commands** (`/tabs /artifacts /bookmarks /history /files /skill /agent /remember`) are the right shape for bringing Chrome context into the ask.
- **The artifact store round-trip** — keyed create-or-update, WAL-compensated in-place update, identity-only tool results — and the viewer, library, dialog and New tab all render updated content correctly; the `asset.update` approval gate is real and cannot be clicked by script.
- **Provider adapters**: OpenAI-compatible and native Gemini lanes both clean; host-origin preflight; secret redaction in logs; 2 s retry spacing.
- **The observability layer** (`cap-perf` spans, `observability.dumpTrace`) made the performance diagnosis fast without extra instrumentation.
- **Test volume and honesty where it runs**: 2457 unit tests, 138/138 journeys, no fixed debugging port anywhere, a TODO count of 2.
